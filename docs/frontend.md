# Frontend

See also: [../ARCHITECTURE.md](../ARCHITECTURE.md), [services.md](services.md), [ui-ux.md](ui-ux.md), [patterns.md](patterns.md)

## Real Structure

- Bootstrapping runs through [src/main.jsx](../src/main.jsx).
- Global app composition in [src/App.jsx](../src/App.jsx) is provider-only: router, route policy, session, cart, notifications, overlay host, window manager, and [src/RootShell.jsx](../src/RootShell.jsx).
- Route declarations and route policy live together in [src/app/routeDefinitions.jsx](../src/app/routeDefinitions.jsx), and [src/app/appRoutes.jsx](../src/app/appRoutes.jsx) mounts those route components without prop injection.
- Global chrome is owned only by [src/RootShell.jsx](../src/RootShell.jsx) plus the shell renderers in `src/shells/*.jsx`.
- Shared API access lives in `src/shared/services/api/*.js`, rooted at [src/shared/services/api/core.js](../src/shared/services/api/core.js).
- Cart state is local-storage backed through [src/providers/CartProvider.jsx](../src/providers/CartProvider.jsx), not by a backend cart API.
- Shared UI primitives and base tokens live in [src/App.css](../src/App.css) and [src/shared/components](../src/shared/components); prefer extending those before introducing feature-local duplicates for recurring surfaces like empty states, cards, and compact action rows.

## State And Orchestration Pattern

- Large pages are controlled by feature hooks, not page components full of side effects.
- Shared app state that crosses routes now lives in dedicated providers instead of route props:
  - [src/providers/SessionProvider.jsx](../src/providers/SessionProvider.jsx)
  - [src/providers/CartProvider.jsx](../src/providers/CartProvider.jsx)
  - [src/providers/NotificationsProvider.jsx](../src/providers/NotificationsProvider.jsx)
  - [src/providers/RoutePolicyProvider.jsx](../src/providers/RoutePolicyProvider.jsx)
  - [src/providers/OverlayProvider.jsx](../src/providers/OverlayProvider.jsx)
- Admin user-management flow details live in [user-management-state-contract.md](user-management-state-contract.md).
- Key examples:
  - [src/features/admin/hooks/useAdminPageController.js](../src/features/admin/hooks/useAdminPageController.js)
  - [src/features/catalog/products/hooks/useProductsController.js](../src/features/catalog/products/hooks/useProductsController.js)
  - [src/features/commerce/purchase/hooks/usePurchaseManagementController.js](../src/features/commerce/purchase/hooks/usePurchaseManagementController.js)
  - [src/features/credits/history/hooks/useCreditHistoryController.jsx](../src/features/credits/history/hooks/useCreditHistoryController.jsx)
  - [src/features/notifications/hooks/useNotificationsInbox.js](../src/features/notifications/hooks/useNotificationsInbox.js)
- Purchase-order entry now uses one shared controller for both admin-inline and popup/browser workspaces:
  - The form stays supplier-first, with desktop step guidance owned inside [src/features/commerce/purchase/components/PurchaseEntryModals.jsx](../src/features/commerce/purchase/components/PurchaseEntryModals.jsx).
  - The create flow should stay `Supplier -> Items -> Review -> Final Submit`, with the first submit only opening the compact review stage and the actual PO save happening on final submit.
  - Popup purchase create should open in a compact supplier-only screen first, and delivery date or note edits should wait until the review stage right before final submit.
  - The item screen should keep only the working PO rows on the board, while supplier selection immediately hydrates that board from the supplier's registered product list and product add/search happens through the separate extra-products picker window.
  - The main entry surface should stay qty-first: new product picks open as quick-entry rows with `0` quantity, those zero-qty rows stay editable in the draft, and only rows with qty above zero should count toward review and final submit.
  - The review stage should read like a compact printed PO sheet with supplier/date metadata, short item lines, subtotal, GST, total, and only the optional note blocks that are actually filled.
  - The item workspace should stay single-column and full-width during entry. Avoid a split pending-PO side panel that forces constant left-right eye movement.
  - When the product picker is open, the pending PO should stay visible in the same screen. Product selection should behave like a visual catalog picker with tappable cards and multi-select tracking, not like a hidden text-search workflow.
  - Keep only one product-add entry point in the PO screen. `Add Product` should open the picker, `Done` should commit the current card selections into the PO draft, and `Cancel` should close the picker without adding rows.
  - The picker should include a `New Product` action that opens the quick-add product form in a modal so operators can add minimum-required product details without leaving the PO flow.
  - The extra-product search should stay lightweight inside the picker window: search by name or SKU, keep the result/availability count visible, and use browser-local filtering so typing does not stall the rest of the PO grid.
  - The extra-product picker should lazy-load catalog cards as the operator scrolls, keeping the initial render compact while still allowing full selection.
  - Supplier-linked rows should load directly onto the PO board as locked defaults: they stay editable for qty/rate/GST/discount but should not expose row removal.
  - Locked supplier-default rows should keep a visible skipped cue while qty stays `0`, and save/reopen flows should preserve whether each PO row came from the supplier board or from a manual extra add.
  - The add-product picker should only show non-supplier catalog items that are not already on the PO board, so extra items stay clearly separate from the supplier default board.
  - Changing the supplier should reset the current draft rows and picker selection so the board always matches the chosen supplier registry.
  - Do not open product creation from inside the PO modal. Missing catalog items should be handled outside the PO create surface so purchase entry stays focused on selection, qty, review, and submit.
  - Saved PO drafts should stay browser-local through [src/features/commerce/purchase/utils/savedDrafts.js](../src/features/commerce/purchase/utils/savedDrafts.js) and be reopenable from both the inline workspace and popup workspace without needing a backend draft route.
  - Repeated `Save Draft` clicks on the same open PO should overwrite the same saved draft entry instead of creating a new one.
  - Popup/browser completion context stays in the same feature tree through [src/features/commerce/purchase/components/PurchaseManagementPageLayout.jsx](../src/features/commerce/purchase/components/PurchaseManagementPageLayout.jsx) and [src/features/commerce/purchase/components/sections/PurchasePopupWorkspacePanel.jsx](../src/features/commerce/purchase/components/sections/PurchasePopupWorkspacePanel.jsx) instead of a separate purchase state system.
  - Post-save purchase completion should stay inside the same feature tree too. [src/features/commerce/purchase/hooks/usePurchaseOrderFormHandlers.js](../src/features/commerce/purchase/hooks/usePurchaseOrderFormHandlers.js) should record the latest saved PO summary without forcing a jump into the purchase-orders table, and [src/features/commerce/purchase/components/sections/PurchaseSavedOrderPanel.jsx](../src/features/commerce/purchase/components/sections/PurchaseSavedOrderPanel.jsx) should provide the shared `View PO`, `New PO`, and manual `Prepare WhatsApp` handoff in both inline and popup workspaces.
  - The admin dashboard may reuse purchase-operations summary data from [src/features/admin/hooks/useAdminDataLoaders.js](../src/features/admin/hooks/useAdminDataLoaders.js) inside [src/features/admin/sections/DashboardSection.jsx](../src/features/admin/sections/DashboardSection.jsx) to open the same purchase feature for three shortcut types: draft creation, PO payment, and PO review. Keep those handoffs flowing through [src/features/admin/hooks/useAdminPageController.js](../src/features/admin/hooks/useAdminPageController.js) and [src/features/commerce/purchase/hooks/usePurchaseManagementController.js](../src/features/commerce/purchase/hooks/usePurchaseManagementController.js) instead of inventing dashboard-owned purchase state.
  - Admin dashboard purchase shortcuts should preserve the concrete supplier when the shared purchase summary points to one. [src/features/admin/sections/DashboardSection.jsx](../src/features/admin/sections/DashboardSection.jsx) may still stay handoff-only, but its `Prepare PO` shortcut should pass `supplier_id` / `supplier_name` through the existing purchase shortcut payload so the shared purchase workspace opens the right supplier board.
  - On small screens, [src/features/admin/sections/DashboardSection.jsx](../src/features/admin/sections/DashboardSection.jsx) may also condense that same purchase summary into one owner quick-view surface for supplier visits, due payments, draft-review work, and pending deliveries, but it should stay handoff-only and keep every purchase action routed through the existing admin purchase shortcut path.
  - Purchase planning may also render supplier novelty alerts from that same summary payload. [src/features/commerce/purchase/components/sections/dashboard/PurchasePlanningPanel.jsx](../src/features/commerce/purchase/components/sections/dashboard/PurchasePlanningPanel.jsx) and [src/features/commerce/purchase/components/sections/PurchaseRemindersSection.jsx](../src/features/commerce/purchase/components/sections/PurchaseRemindersSection.jsx) should only present `distributor_insights[*].novelty_*` metadata produced by the server summary, not recalculate catalog or recent-habit checks in the browser.
  - The purchase planning dashboard should stay operator-routine-first: [src/features/commerce/purchase/components/sections/dashboard/PurchasePlanningPanel.jsx](../src/features/commerce/purchase/components/sections/dashboard/PurchasePlanningPanel.jsx) should group the next 7 days by schedule date, use `weekly_distributors` as the board row source, join the server-backed `supplier_visits` overlay by `supplier_id + date`, and treat `poDone || visitClosed` as the handled rule for removing rows from the active list. Active supplier rows should stay compact and scan-first with one top identity line, one bottom status/prep line, icon-only PO/payment/novelty state, and a single overflow actions menu; the only manual routine action is today's persisted `Close Visit` / `Reopen`, and old browser-local move, skip, and no-action handling should not drive the live board anymore.
  - The purchase dashboard should open directly into the routine board inside [src/features/commerce/purchase/components/sections/PurchaseDashboardSection.jsx](../src/features/commerce/purchase/components/sections/PurchaseDashboardSection.jsx). Do not reintroduce a separate dashboard hero with summary cards, quick-action tiles, sector-switch tiles, or extra payables/deliveries/workflow/insights blocks above or below that routine surface.
  - The supplier routine metrics in [src/features/commerce/purchase/components/sections/dashboard/PurchasePlanningPanel.jsx](../src/features/commerce/purchase/components/sections/dashboard/PurchasePlanningPanel.jsx) should render as stat cards, not bespoke summary cards, so the top metrics read like compact routine stats.
  - Dashboard planning handoff into PO create should respect the concrete schedule entry. When a day-wise supplier row opens a draft, [src/features/commerce/purchase/hooks/usePurchaseOrderFormHandlers.js](../src/features/commerce/purchase/hooks/usePurchaseOrderFormHandlers.js) should prefer the selected `supplier_id` from that planning entry instead of falling back to the distributor primary supplier, and it should pass the row date as explicit `planned_order_date` instead of leaving the visit anchor implicit in `expected_delivery`.
  - The purchase WhatsApp handoff is still manual launcher flow. [src/shared/services/api/purchaseOrders.js](../src/shared/services/api/purchaseOrders.js) should treat `POST /api/purchase-orders/:id/distributor-whatsapp` as a preparation/open action through `prepareDistributorWhatsApp`, while the older `sendDistributorWhatsApp` name remains only as a compatibility alias for existing callers.
  - Final review and manual WhatsApp preparation should stay inside the shared PO detail modal in [src/features/commerce/purchase/components/modals/OrderDetailModal.jsx](../src/features/commerce/purchase/components/modals/OrderDetailModal.jsx) rather than forcing a separate jump into the purchase-orders table for the send path.
  - The PO detail modal should reuse the same printed-bill review sheet styling as the draft review step so saved-PO review stays visually consistent.
  - The confirm PO modal should keep a single checked-by-default `Mark as delivered` control above payment inputs and submit the delivered flag through the existing confirm path instead of inventing a second delivery workflow.
  - Draft item auto-fill should follow one rule across supplier-board loading, manual entry, and restock handoff: prefer the latest PO values from the selected supplier for that product, otherwise fall back to the latest PO for that product from any supplier, and only then use product defaults.
  - The PO create shell should stay compact: workflow order can remain visible, but helper copy, repeated status summaries, and large action rows should be replaced by short pills and compact icon-led controls where the action is still obvious.
  - The POS item list inside purchase create should stay row-like: use one flat inline grid per product with image/name, qty, unit, rate, GST, discount, and total instead of stacked card blocks or expandable mini-forms, and keep any confirm/remove actions tucked into the line total area rather than a separate status column.
  - The purchase discount column should behave as one draft-wide mode controlled by the grid header. Toggling `Disc %` and `Disc ₹` may reuse the same row input field, but the switch should reset current draft discount values instead of silently reinterpreting them.
  - Purchase create should now mount as a dedicated fixed full-screen workspace overlay. Keep the supplier-first workflow, but remove the floating dialog feel, lock background scrolling while it is open, and do not let the create screen keep draggable, resizable, or repositionable window behavior.
  - The purchase workspace itself should stay structurally stable: keep the main header/footer anchored, avoid nested page-plus-modal scrolling, and let the item board own the main scroll behavior during row entry.
  - Keep the main path light: supplier step should only unlock the supplier, optional delivery/notes should live in review-side extras, supplier defaults should load immediately without a `Show All` gate, and the sticky footer should own the main order total instead of repeating totals across the screen.
  - Item entry should stay focused on supplier board rows and extra product adds only. Do not keep delivery-date or note cards in the supplier step or item step when those values can be updated in review before final submit.
  - Inactive catalog products should not load into the draft from supplier-board hydration, search suggestions, history suggestions, or restock handoff; only active catalog rows belong in the live purchase workspace.
  - The live PO item grid should keep the Product search control next to the Product header, sort the Product column in place, and filter only the loaded rows by row name or SKU without leaving the working screen.
  - Keep secondary row fields inline and keyboard-friendly. GST, UOM, discount, and similar row edits should sit directly in the same flat row as qty and rate so operators can tab across the line without opening per-row drawers or edit states.
- Billing should stay compact around the existing `items -> bill -> checkout` flow:
  - [src/features/sales/billing/components/BillingTabView.jsx](../src/features/sales/billing/components/BillingTabView.jsx), [src/features/sales/billing/components/BillingProductForm.jsx](../src/features/sales/billing/components/BillingProductForm.jsx), [src/features/sales/billing/components/BillingBillList.jsx](../src/features/sales/billing/components/BillingBillList.jsx), [src/features/sales/billing/components/BillingSummary.jsx](../src/features/sales/billing/components/BillingSummary.jsx), and [src/features/sales/billing/components/BillingPaymentPanel.jsx](../src/features/sales/billing/components/BillingPaymentPanel.jsx) should prefer short labels, terse helper text, smaller supporting type, and reduced card spacing instead of explanatory paragraphs and repeated status language.

- Admin daily-sales cash state should stay inside the admin feature tree:

## Change Rules

- Keep feature state inside the owning feature tree.
- Reuse existing controller-hook and builder-helper patterns before adding new top-level state.
- Do not reintroduce route prop injection for shell-owned data. Session, cart, notifications, route policy, and overlay ownership already have provider boundaries.
- Do not let pages or feature layouts decide header/footer visibility. Route policy chooses the shell variant and the shell owns chrome.
- If shell/runtime ownership changes, run `npm run check:shell-runtime` and `npm run test:shell-runtime` before sign-off.
- If a frontend API wrapper changes, verify it still matches [../ROUTES.md](../ROUTES.md).
- Do not add wrappers for endpoints that do not exist in [../ROUTES.md](../ROUTES.md). Cart remains local-only unless backend routes are added and documented first.
- Keep admin user search backend-owned. The current `/api/users` contract is simple server-side `LIKE` search; if scalability changes are needed, extend the backend search implementation without changing the frontend query model first.
- Keep product-image failure handling presentation-only. Remote product image URLs may still fail at the browser/network layer, but shared product-image rendering should fall back to the generated placeholder in [src/shared/components/product/SafeProductImage.jsx](../src/shared/components/product/SafeProductImage.jsx) instead of leaving broken-image UI states behind, and known-bad remote image hosts may be skipped entirely in [src/shared/utils/productImage.js](../src/shared/utils/productImage.js) so the browser does not keep retrying broken SSL endpoints.
- Keep the customer credit-history monthly statement view presentation-only. It may summarize the ledger by month for readability, but it must continue to consume `credit_history` and `paymentBadgeSummary` rather than inventing a parallel statement source of truth.
- Keep customer credit-history grouping and identity emphasis presentation-only. Visible entries may be grouped by effective transaction date and the header may emphasize customer identity, but per-entry balances, ordering semantics, and ledger actions must continue to come from the underlying `credit_history` rows.
- Keep credit-history badge guidance contract-driven. The header helper text and monthly-statement pay-by note must reuse `paymentBadgeSummary.helper_text`, `maintain_score_by_date`, `grace_days`, and `next_status_label` rather than inventing separate due-date or upgrade logic in the browser; `maintain_score_by_date` is the active oldest-unpaid cycle deadline, not a raw stored entry due date.
- Keep the admin credit-aging screen honest about snapshot state. If `/api/credit/aging` reports `503 { status: "initializing" }`, the UI should show an updating/rebuild state instead of a generic failure or stale customer health data.
- Keep the admin restock dashboard as a local counted-stock workspace until sync. The Products-side restock page may hold counted stock drafts, selection state, selected-item PO quantities, sort state, and product-specific supplier filtering locally in the browser, but live stock must only change through the shared stock-adjustment API, the Stock History page stays the audit/reference surface, and PO handoff must reuse the purchase workspace instead of inventing a second PO flow. Restock may open the PO draft before a supplier is chosen; the PO flow should still start with the supplier step and apply restock-selected quantities only after the supplier board is loaded. That handoff may carry a lightweight product UOM snapshot so the PO draft does not break on stale cached purchase lookups after recent product-unit edits.
- Keep restock-to-PO review state inside the restock feature instead of inventing a second purchase draft system. The editable pre-handoff review surface in [src/features/admin/sections/RestockDashboardSection.jsx](../src/features/admin/sections/RestockDashboardSection.jsx) may collect PO quantities, a review-level supplier choice, optional delivery, and notes, but it should still hand off into the shared purchase workspace for final PO creation rather than creating purchase orders directly from the restock page.
- Keep operator-facing wording consistent with the business meaning. Purchase and restock UI should say `Supplier` for the human-facing label even when the persisted field names remain `distributor_*` internally for compatibility.
- Keep restock-linked PO drafts temporary. When a PO draft was opened from restock selection, cancelling that draft or removing all meaningful rows should close the PO and return the admin workspace to the restock dashboard instead of leaving an empty purchase draft behind.
- Restock-to-PO should open the inline purchase workspace even if a purchase popup is already open. Keep the restock review saved for retry if an inline draft is busy, and avoid forcing a new browser window for restock handoff.
- Keep the restock workspace compact. The top restock bar and PO review card should prefer short count/status pills plus compact icon-led actions over repeated explanatory copy, duplicate distributor/filter summaries, or large stacked action buttons.
- Keep purchase create completion visible in popup mode. The popup/browser purchase workspace may render recent PO context and the latest saved PO next to or under the inline form, but it should keep using the shared purchase-orders list/detail handlers instead of inventing popup-only completion state or routes.
- That shared purchase-orders list should keep scoped search honest: changing the scope should apply the visible draft text immediately, and the search placeholder/accessibility copy should follow the selected scope instead of staying in broad `PO or Supplier` wording while the mode is narrowed.
- The purchase payments tab in [src/features/commerce/purchase/components/sections/PurchasePaymentsSection.jsx](../src/features/commerce/purchase/components/sections/PurchasePaymentsSection.jsx) should mirror the stock-ledger shell: use `BackofficePageHeader`, a search/filter bar, active filter pills, an advanced supplier/view/date tray, summary cards, and one sticky compact scroll container that holds the due-supplier rows plus the ledger history; show `Confirm` for unconfirmed POs and `Pay` only once payment is allowed, and keep supplier labels with distributor context in the filter/options and row labels even while the compatibility filter key remains `distributor_id`.
- A fully paid purchase order should be close-only in the purchase UI. Hide `Add Payment` once the PO reaches `fully_paid`, and keep the close action as the only next step after settlement.
